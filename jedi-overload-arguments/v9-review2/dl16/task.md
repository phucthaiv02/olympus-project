Fix Jedi to choose the correct overload based on the type of the arguments in the call. For example, there are two overloads `get_obj(input: type[Foo]) -> FooBuilder` and `get_obj(input: type[Bar]) -> BarBuilder`. When typing `get_obj(Foo).`, Jedi should only suggest `FooBuilder` methods.

Jedi should use the first overload that accepts all arguments, whether they are passed by position or by name, and only combine the results of all overloads when there are no matching overloads. Annotations follow normal typing rules. In the examples below, `A` and `C` are two unrelated classes. When calling `f(A if c else C)`, the overload with parameter `x: type[A]` is not selected, because the argument could be `C`. Similarly, if `xs` has type `list[type[C]]`, then `f(*xs)` can pass any number of arguments, including no arguments, so Jedi does not choose an overload with exactly one `x: type[C]` parameter.

With tuples, lists and dicts written directly in the code, Jedi should look at the actual content that Python creates at runtime. This is still true when they are in a variable, unpacked with `*` or `**`, or nested like `f(*[A, *b])`. For example, in `{1: A, True: C}`, the two keys are equal, so the value written later overwrites the value written before, and the dict only has the value `C`. In `{"k": C, **d}`, if `d` can be `{"k": A}` or `{}`, then the value of `"k"` can be `A` or `C`. A comprehension on an empty literal, for example `[C for _ in []]`, produces no elements. With `xs = [A] if c else []`, when calling `f(*xs, C)`, `C` can be the first or second argument.
