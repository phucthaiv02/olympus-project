Fix the order in which GopherJS evaluates assignments, calls and composite literals so that programs behave as the Go specification's order of evaluation requires. Programs that depend on this order currently produce different results, or call functions in a different order, than they do with the gc compiler.

Assignments must happen in two phases. First, the operands of index expressions and pointer indirections on the left-hand side (including the implicit indirection in a selector such as `p.f`) and the expressions on the right-hand side are evaluated, with all function calls, method calls and channel receives happening in lexical left-to-right order. Only then are the assignments carried out, left to right, so an element or field on the left is chosen with the values its operands had before the statement. This applies to assignments with several values, to assignments from a multi-value call, and to range loops that assign to existing variables. In a map element assignment the map operand is evaluated before the key. A run-time panic caused by the assignment itself, such as an index out of range or an assignment to an entry in a nil map, only happens after the right-hand side has been evaluated, and assignments that come before the failing one in the same statement still take effect.

In a function or method call the function value, including any calls needed to compute it or its receiver, is evaluated before the arguments. This must also hold when the arguments are the results of a multi-value call, and when an argument itself contains such a call. The elements of composite literals, including struct literals with field names and array or slice literals with explicit indices, are evaluated in the order they are written rather than in field or index order.

All of this must also hold when some of the calls involved block.
